### 失败集中在四类，不是随机错

1. **R6（差评爆发）依然是最容易误报的根因**：D15/D17/D20/D22/D25 都以 R6 开头。
   差评率是「十几条评价上的比率」，一条差评就能把比率从 1.5% 顶到 8%，而 z 检验在
   这种分母下本来就不稳。本轮已加三道闸（稀有事件分母门槛、事件数 ≥3、z ≥2.2、
   评分封顶），把 R6 从 10 次 top-1 压到 5 次，但还没根治。
2. **R1（竞品降价）与 R9（价格带错配）几乎检不出**（D01/D02/D19）。它们主要靠
   `cvr` 下滑 + 竞品价差，而 `cvr` 下滑与 R4/R6/R7 共用同一个症状，竞品价差又要
   SKU 级对齐才有意义；当前只在 SKU 维度算 `competitor_gap`，全店/款式级没有。
3. **窗口尾段滞后**（D14 11-15 真值 R7、D05 11-14 真值含 R7）：R7 的注入窗口是
   11-12~11-18，11-15 正处中段，但系统把「大促后流量下滑」归成了 R3/R1。这是
   促销口径与流量衰减叠加的老问题，`promo_dominated` 只给了 caveat，没参与排序。
4. **多真值场景天然吃亏**：25 条里 14 条 gold 有 2~3 个根因，而系统平均只出 1.88 张卡，
   top-3 命中率因此被结构性地压住（出卡少 → 覆盖不足）。

## 4. T7 期间修掉的三处引擎问题

评测暴露问题后，先修引擎再定阈值（顺序不能反，否则就是「改考题迁就学生」）。

| 问题 | 证据 | 改法 |
|---|---|---|
| 稀有事件噪声主导排序 | 10-10 一条 `neg_review_rate +450%`（12 条评价里 1 条差评）score 3.20，压过所有真实下滑 | `RARE_EVENT_METRICS` 要求事件数 ≥3、`RARE_Z_MIN=2.2`；score 的相对变化封顶 100% |
| 退款原因与根因无关，R4/R10 无法区分 | 生成器 `REFUND_REASONS` 固定权重，R4 与 R10 都只表现为「退款率上升」 | 数据 v2：R4 窗口内 80% 记 `SIZE_SMALL`、R10 窗口内 80% 记 `LOGISTICS`（`tools/migrate_refund_reasons.py`，已回填现库） |
| R6 只认差评率，误删「评分掉但差评率没起」的真 R6 | 08-20 的 R6 卡被复审以「宽窗查不到 neg_review_rate」删掉 | R6 改为双证据：`critic.REQUIRED_SUPPORT[R6]="dsr"`、replan 不再把 R6 当必需辅证；hypothesis 里 dsr 权重 0.70→0.80 |

## 5. 消融实验

### 5.1 召回：FTS 单独 vs 混合（7 条检索 query）

| 档位 | 命中率 | top-1 精确率 | 召回 | 耗时 |
|---|---|---|---|---|
| fts-only | 0.857 | 0.714 | 0.857 | 0.68s |
| **hybrid（FTS+向量 RRF）** | **1.000** | **0.857** | **1.000** | 19.4s（含 bge-m3 冷启动 ~18s，热态 0.2s） |

→ 向量召回补上了 FTS 漏掉的那条（「热销款断货」这类 2 字词，trigram 需要 ≥3 字连续片段）。

### 5.2 重排：off / rule / cross（7 条）

| 档位 | 命中率 | top-1 精确率 | 耗时 |
|---|---|---|---|
| off | 1.000 | 0.857 | 20.0s |
| rule | 1.000 | 0.857 | 2.0s |
| cross | 1.000 | 0.857 | 32.6s |

→ **这一组没拉开差距**：7 条 query 都带明确根因关键词，hybrid 召回后首条就对了，重排无从发挥。
诚实结论：这组消融证明「重排不劣化」，不证明「重排有用」；要证明得用更难的 query（同义改写、无关键词）。
cross 档 32.6s 里约 18s 是 cross-encoder 冷启动，也是默认 `RERANK_MODE=rule` 的原因。

### 5.3 第二轮复审：on vs off（10 条诊断）

| 档位 | 命中率 | 精确率 | 召回 | 耗时 |
|---|---|---|---|---|
| replan=off | 0.600 | 0.392 | 0.417 | 10.2s |
| replan=on | 0.600 | **0.467** | 0.367 | 14.4s |

→ 复审把精确率抬高 7.5 个点，代价是召回掉 5 个点、每条多 0.4s。这与设计意图一致：
它靠「撤掉无法复核的卡」换准，而不是靠补卡换全。

## 6. 与 spec 目标的差距（要说清楚）

| 指标 | spec §3.8 目标 | 实测 | 差距 |
|---|---|---|---|
| 问数四项全对 | ≥0.90 | **1.000** | 达标 |
| 归因 top-3 | ≥0.80 | **0.520** | **差 28 点** |
| 端到端（诊断卡可用） | ≥0.75 | 0.440（top-1） | 差 31 点 |
| 素材字段准确率 | ≥0.85 | 1.000（mock）/ 0.883（vlm） | 达标 |
| 单条诊断耗时 | ≤3s | 1.48s（均值） | 达标 |

差距的原因不是「阈值定低了」，而是规则版归因的上限：症状→根因的映射是一张固定表，
多真值、促销期、滞后指标三类场景都吃不下来。**要继续往上推，需要的是 Critic 触发重规划
之外的两种能力**：①按 SKU 聚合竞品价差并参与 R1/R9 排序；②把「多真值」当常态——
每张卡只解释一部分成交损失，输出卡片集合而不是单一结论。

## 7. 已知限制

- **诊断真值只有 10 类注入根因**，评测覆盖的是「人造异常」，不是真实店铺的长尾问题。
- **`anomaly_gt` 的窗口是注入窗口**，评测按「窗口与巡检窗口有交集」取真值；窗口边界上
  的用例（如 D14）对边界敏感。
- **素材 1.000 是 mock 回放**，不代表模型能力；vlm 档的残余错误集中在文字占比（±0.10 容差边缘）
  与场景混淆（度假 ↔ 街拍）。
- **动作套件全绿**，但执行器是 mock（只写 `store_state`），护栏之外的真实平台约束（库存、审核、限流）没有覆盖。
- 消融 5.2 的 query 太容易，结论只能用作「不劣化」的证据。

## 8. 怎么跑

```bash
cd project

# 全量（4 个套件 + 门禁），有套件低于阈值时退出码 1
python -m app.eval.runner --db data/store.db

# 单套件 / 只看前 N 条 / 存 JSON
python -m app.eval.runner --suite diagnose --limit 5 --json --out .tmp/eval.json

# 消融：召回 / 重排 / 复审
python -m app.eval.ablation --kind retrieval
python -m app.eval.ablation --kind pipeline --limit 10

# 素材真机（会调视觉模型，按张计费，先确认 VISION_MODE）
VISION_MODE=vlm python -m tools.vision_eval --mode vlm --cases 10
```

门禁阈值在 `app/eval/gate.py` 的 `GATE_DEFAULTS`；改引擎后先跑评测，再决定要不要动阈值。
